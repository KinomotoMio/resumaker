# 履历即代码 · Career as Code

> 简历不是"写"出来的，是从你的履历库里，针对一份 JD"编译"出来的。

大多数人写简历的方式是：要投递了，打开一个空白文档，开始回忆过去一两年干了什么。
问题是——**你记不住**。八个月前那次性能优化到底把 P99 降了多少？那个方案为什么选了 A 而不是 B？
写简历时想不起来，面试被追问时更想不起来。

Resumaker 想教的是另一种习惯：**把履历当成一个持续维护的代码仓库**。

---

## 六条原则

### 1. 趁热记录，别等到写简历才回忆

做完一件值得说的事，当天就记一笔，哪怕只有三行。
最好的素材是"刚发生的"：数字还在看板上，PR 还没被淹没，踩过的坑还记得清楚。

如果你每天都在和 Agent 协作，这一步甚至可以自动化——开启 [被动采集](../skills/career-harvest/SKILL.md)，
让 Agent 在会话结束后帮你起草，你只负责确认。

### 2. 一件事一个文件

履历库的最小单位是 **成果（achievement）**，不是"项目"，更不是"一份简历"。

```
achievements/2025-03-ws-gateway-perf.md   ← 一次具体的、有结果的事
projects/realtime-gateway.md              ← 容器：这些成果发生在哪个项目
experiences/2024-07-acme.md               ← 容器：这个项目发生在哪段经历
```

原子化的好处：同一个项目里的五件事，投不同岗位时可以各取所需，而不是整段复制粘贴。

### 3. 数字要有出处

每个数字都写上它从哪来：监控截图、PR 链接、周报、某次会话。
没有出处的数字，在库里标记为 `verified: false`，生成简历时会被提醒。

这不是为了严肃，而是为了**面试时不心虚**。

### 4. 一件事，多种讲法

"把 WebSocket 网关的 P99 从 320ms 降到 85ms"——

- 投 **基础架构** 岗：讲连接模型重构、epoll、内存池
- 投 **业务/全栈** 岗：讲用户可感知的卡顿下降、对留存的影响
- 投 **技术管理** 岗：讲如何推动跨组压测、灰度方案

这些不同的"角度（angles）"提前写在成果文件里，定制简历时直接挑。
**"把项目写成对口的"，本质上就是选对角度。**

### 5. 简历是编译产物

```
履历库  +  JD  ──编译──▶  匹配报告 + 简历 + 面试深挖卡
```

一份 JD 对应一个 `applications/<日期>-<公司>-<岗位>/` 目录。
简历里每一条 bullet 都能追溯回某个成果文件——库里没有的，就不写。
海投一份通用简历，等于用同一个二进制跑所有平台。

### 6. 写进简历的，就要能被追问

面试官是看着你的简历出题的。所以每次编译简历时，顺便生成一份
**深挖卡**：每条 bullet 可能被追问什么、你的真实素材是什么、哪里是薄弱点。

简历和面试准备，是同一件事的两面。

## 一个典型的节奏

| 什么时候 | 做什么 | 用哪个 skill |
|---|---|---|
| 第一次 | 建库，导入旧简历 / GitHub / 周报 | `resumaker-init` → `career-capture` |
| 平时 | 做完一件事随手记一笔；或让 Agent 自动起草 | `career-capture` / `career-harvest` |
| 每周 / 每月 | 花 10 分钟过一遍草稿箱 | `career-review` |
| 看到心仪的 JD | 编译一份对口简历 + 匹配报告 | `resume-tailor` → `resume-render` |
| 面试前 | 对着简历被"拷打"一遍 | `interview-grill` |
| 投完之后 | 记录结果，回头看哪种讲法更有效 | `resume-tailor`（更新 `notes.md`） |

## 履历库长什么样

见 [`skills/resumaker-init/assets/vault/VAULT.md`](../skills/resumaker-init/assets/vault/VAULT.md)——
